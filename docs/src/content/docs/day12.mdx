## 今日つくるもの

- `app/internal/metrics/metrics.go`
  - `RecordHTTPRequest(method, route string, status int, duration time.Duration)` で、method・route・status ごとのリクエスト数と、route ごとの処理時間を記録する。
  - `RecordCacheHit()` と `RecordCacheMiss()` で、キャッシュの hit と miss を別々の counter に記録する。
- `app/internal/middleware/status.go`
  - `newStatusResponseWriter(w http.ResponseWriter) *statusResponseWriter`、`WriteHeader(status int)`、`Write([]byte) (int, error)`、`Unwrap() http.ResponseWriter` を実装する。
  - status を明示しないレスポンスは 200 として扱い、最初に書かれた status を保持し、元の `http.ResponseWriter` へ処理を委譲できるようにする。
- `app/internal/middleware/metrics.go`
  - `Metrics(next http.Handler) http.Handler` で、下流の処理後に HTTP method・正規化した route・status・処理時間を記録する。
  - `routeLabel(r *http.Request) string` で、空の route は `unknown`、`/{code}` は `redirect` とし、method 付きの pattern から path 部分を取り出す。短縮コードそのものをラベルにしない。
- `app/internal/middleware/requestlog.go`
  - `RequestLogger(logger *slog.Logger) func(http.Handler) http.Handler` で、各 HTTP リクエストの `method`、`path`、`status`、`duration_ms`、`remote` を構造化ログに出す。
  - `remoteAddr(r *http.Request) string` で、`X-Forwarded-For` があれば先頭の値を優先し、なければ接続元アドレスから host を取り出す。
- `app/cmd/server/main.go`
  - `newLogger() *slog.Logger` で JSON logger を作り、`LOG_LEVEL` の `debug`、`warn` / `warning`、`error` と、既定の `info` を反映する。
  - `fatal(msg string, args ...any)` で致命的なエラーを構造化ログへ記録して終了する。
  - `GET /metrics` を公開し、アプリへ metrics middleware と request logger を接続する。
- `app/internal/cache/redis.go`
  - Redis の hit と miss を既存の統計に加えて Prometheus counter にも記録する。Redis の失敗は構造化ログへ残し、これまでどおり storage へフォールバックする。
- `deploy/compose.monitoring.yaml`、`deploy/prometheus/prometheus.yml`
  - Compose に Prometheus と Grafana を追加し、Prometheus が 15 秒間隔で `app:8080/metrics` を scrape できるようにする。

  - Prometheus datasource と `Shortlink RED and Cache` dashboard を自動登録し、Request Rate、Error Rate、Latency p95、Cache Hit Ratio を表示する。

## 解説

Day 11 では、URL 短縮サービスを水平スケールしやすい形へ近づけました。Pod を増やせるようになったら、次に必要なのは「増やしたあと何が起きているかを見られること」です。何 req/s 来ているのか、5xx は増えているのか、p95 レイテンシは悪化しているのか、Redis キャッシュは効いているのか。これらを人間の勘ではなく、機械的に答えられる形にします。

### 可観測性の三本柱

可観測性では、よく三本柱という言い方をします。メトリクス、ログ、トレースです。

メトリクスは、数値を時系列で集めたものです。Prometheus は、アプリの `/metrics` を定期的に取りに行き、PromQL で問い合わせられるようにします。たとえばリクエスト数、エラー率、p95 レイテンシ、キャッシュヒット率です。

ログは、ある時点で起きたイベントの記録です。今日のアプリは HTTP リクエストごとに `method`、`path`、`status`、`duration_ms`、`remote` を JSON で出します。メトリクスで「5xx が増えた」と分かったあと、どのリクエストが失敗したのかを追うときに使います。

トレースは、1 つのリクエストが複数サービスをまたいで流れる様子を追うものです。API、DB、外部 API のどこで時間を使ったかを span として見ます。Day 12 では実装しませんが、メトリクスで異常を見つけ、ログで詳細を絞り、必要ならトレースで経路を見る、という役割分担を覚えておきましょう。

### RED メソッド

Web API の入口を見るときは、RED メソッドが便利です。RED は Rate、Errors、Duration の頭文字です。

Rate は流量です。shortlink なら、`POST /api/links` や `GET /{code}` が何 req/s 来ているかを見ます。Errors はエラー率です。HTTP なら 5xx の割合、場合によっては 404 の急増も見ます。Duration は処理時間です。平均だけでなく、p95 や p99 を見ます。一部のユーザーだけ極端に遅い状態は、平均値では見逃されやすいからです。

### counter、gauge、histogram

Prometheus のメトリクス型は、意味を分けて使います。counter は増えるだけの値です。`http_requests_total` はリクエストごとに 1 増えます。`cache_hits_total` と `cache_misses_total` も、ヒットやミスのたびに増えます。

gauge は増えたり減ったりする現在値です。現在の goroutine 数、キュー長、メモリ使用量のような値に向いています。今日のカスタムメトリクスには gauge はありませんが、「今いくつか」を表す型です。

histogram は、観測値をバケットに分けて数えます。今日の `http_request_duration_seconds` は、リクエスト時間を histogram として記録します。`0.005 秒以下が何件、0.01 秒以下が何件...` のように累積バケットを持ちます。

<details>
<summary>実装を見る（先に自分で書いてから開こう）</summary>

```go title="app/internal/metrics/metrics.go"
HTTPRequestsTotal = promauto.NewCounterVec(
	prometheus.CounterOpts{Name: "http_requests_total"},
	[]string{"method", "route", "status"},
)
HTTPRequestDurationSeconds = promauto.NewHistogramVec(
	prometheus.HistogramOpts{Name: "http_request_duration_seconds", Buckets: prometheus.DefBuckets},
	[]string{"route"},
)
CacheHitsTotal = promauto.NewCounter(prometheus.CounterOpts{Name: "cache_hits_total"})
CacheMissesTotal = promauto.NewCounter(prometheus.CounterOpts{Name: "cache_misses_total"})
```

`http_requests_total` は `method`、`route`、`status` の組み合わせごとに系列が分かれます。たとえば `GET` の `redirect` で `302`、`POST` の `/api/links` で `201` です。

</details>

### なぜ平均ではなく p95 を見るのか

平均は便利ですが、遅いリクエストを隠します。100 リクエストのうち 99 件が 10ms、1 件が 2 秒なら、平均は約 30ms です。平均だけなら悪くなさそうですが、2 秒待たされたユーザーは困っています。

p95 は、速い順に並べたとき 95% のリクエストがその時間以下で終わった、という値です。Prometheus の histogram は個々の観測値を全部保存せず、バケットごとの累積数を保存します。そのバケットから「95% 点はこのあたり」と推定する関数が `histogram_quantile` です。

```promql title="route ごとの p95 レイテンシ"
histogram_quantile(
  0.95,
  sum(rate(http_request_duration_seconds_bucket[1m])) by (le, route)
)
```

`le` ラベルはバケット境界です。`histogram_quantile` はバケット境界ごとのカウントが必要なので、`sum by (le, route)` のように `le` を残して集計します。

### ルートラベルとカーディナリティ

Prometheus は、ラベルの組み合わせごとに別の時系列を作ります。この系列数の多さをカーディナリティと呼びます。短縮コードをそのままラベルに入れると、`/abc1234`、`/x9Yz001` のようにコードの数だけ系列が増えます。リンクが 100 万件あれば、Prometheus 側にも大量の系列ができます。

そのため Day 12 の middleware は、`/{code}` を `redirect` に正規化します。

```go title="app/internal/middleware/metrics.go"
if pattern == "/{code}" {
	return "redirect"
}
```

個々の code はログや DB で追えば十分です。メトリクスのラベルには、集計軸として意味があり、値の種類が増えすぎないものを選びます。

Day 13 のレートリミットで返る 429 は、ルーティング前に拒否されるため `route="unknown"` として記録されます。

### HTTP middleware で記録する

メトリクスは HTTP middleware で記録します。開始時刻を取り、下流のハンドラを呼び、ステータスと経過時間を記録します。

<details>
<summary>実装を見る（先に自分で書いてから開こう）</summary>

```go title="app/internal/middleware/metrics.go"
start := time.Now()
rec := newStatusResponseWriter(w)
next.ServeHTTP(rec, r)
metrics.RecordHTTPRequest(r.Method, routeLabel(r), rec.status, time.Since(start))
```

標準の `http.ResponseWriter` は、あとからステータスコードを読めません。そのため `statusResponseWriter` で `WriteHeader` を包み、実際に返したステータスを覚えます。この部品があるので、`http_requests_total{method="GET",route="redirect",status="302"}` のような実カウントが取れます。

</details>

### `/metrics` を公開する

Prometheus は、アプリから push してもらうのではなく、自分から scrape しに行きます。アプリ側は `/metrics` を公開します。

<details>
<summary>実装を見る（先に自分で書いてから開こう）</summary>

```go title="app/cmd/server/main.go"
mux.Handle("GET /metrics", promhttp.Handler())
mux.Handle("/", appHandler)
h := middleware.RequestLogger(logger)(middleware.Metrics(mux))
```

`promhttp.Handler()` は、登録済み collector を Prometheus のテキスト形式で返します。Go ランタイムの標準メトリクスに加えて、Day 12 の `http_requests_total`、`http_request_duration_seconds_bucket`、`cache_hits_total`、`cache_misses_total` も出ます。

`/metrics`、`/healthz`、`/readyz` は監視や probe のためのインフラ由来のリクエストなので、RED のリクエストメトリクスとリクエストログからは除外します。

</details>

### キャッシュヒット率を見る

Day 8 の Redis cache-aside は、Day 12 で Prometheus から見えるようになりました。hit と miss は counter として増やします。

<details>
<summary>実装を見る（先に自分で書いてから開こう）</summary>

```go title="app/internal/cache/redis.go"
if url, err := s.client.Get(ctx, key); err == nil {
	s.hits.Add(1)
	metrics.RecordCacheHit()
	return url, nil
} else {
	s.misses.Add(1)
	metrics.RecordCacheMiss()
	if !errors.Is(err, redis.Nil) {
		slog.Warn("redis get failed; falling back to storage", "code", code, "error", err)
	}
}
```

</details>

キャッシュヒット率は、hit の rate を hit と miss の rate の合計で割ります。

```promql title="キャッシュヒット率"
(sum(rate(cache_hits_total[1m])) or vector(0))
/
clamp_min((sum(rate(cache_hits_total[1m])) or vector(0)) + (sum(rate(cache_misses_total[1m])) or vector(0)), 0.001)
```

同じ code に繰り返しアクセスすると、最初は miss、その後は hit になりやすいため、値は 1 に近づきます。

### 構造化ログ

Day 12 の `cmd/server/main.go` は、標準ライブラリの `log/slog` を JSON handler で使います。ログレベルは `LOG_LEVEL` で `debug`、`warn`、`error`、既定の `info` を選べます。

<details>
<summary>実装を見る（先に自分で書いてから開こう）</summary>

```go title="app/internal/middleware/requestlog.go"
logger.Info("http request",
	"method", r.Method,
	"path", r.URL.Path,
	"status", rec.status,
	"duration_ms", float64(time.Since(start).Microseconds())/1000,
	"remote", remoteAddr(r),
)
```

</details>

実際のログは 1 行 JSON です。

```json title="アプリのリクエストログ例"
{"time":"...","level":"INFO","msg":"http request","method":"GET","path":"/abc1234","status":302,"duration_ms":1.42,"remote":"172.20.0.1"}
```

構造化ログが grep より強い理由は、フィールドで機械的に絞れることです。`status == 500`、`method == "POST"`、`duration_ms > 1000` のように、名前と型を使って検索できます。さらに Loki、Elasticsearch、Cloud Logging のような集約基盤へ流せば、Pod が何個あっても同じクエリで探せます。

```promql title="Grafana ダッシュボードの主なクエリ"
(sum(rate(cache_hits_total[5m])) or vector(0)) / clamp_min((sum(rate(cache_hits_total[5m])) or vector(0)) + (sum(rate(cache_misses_total[5m])) or vector(0)), 0.001)
```

### PromQL 入門

`http_requests_total` は累積 counter です。流量を見るには、一定時間あたりの増加率にします。

```promql title="直近 1 分のリクエスト増加率"
rate(http_requests_total[1m])
```

ルートごとの req/s は `sum by` でまとめます。

```promql title="route ごとの req/s"
sum(rate(http_requests_total[1m])) by (route)
```

5xx エラー率は、5xx の rate を全体の rate で割ります。

```promql title="5xx エラー率"
(sum(rate(http_requests_total{status=~"5.."}[1m])) or vector(0)) / clamp_min(sum(rate(http_requests_total[1m])), 0.001)
```

5xx が一度も発生していないと、`status=~"5.."` に一致する系列がなく、左辺が `no data` になります。`or vector(0)` を足すと、エラーがない状態を欠損ではなく 0 として表示できます。

p95 レイテンシとキャッシュヒット率は、先ほどの `histogram_quantile` と hit/miss の式で確認します。

`GET`、`redirect`、`302` の系列が出ていれば、リダイレクトの counter から rate を計算できています。続けて、ルートごとの rate、p95、キャッシュヒット率を確認します。

```promql
sum(rate(http_requests_total[1m])) by (route)
histogram_quantile(0.95, sum(rate(http_request_duration_seconds_bucket[1m])) by (le, route))
(sum(rate(cache_hits_total[1m])) or vector(0)) / clamp_min((sum(rate(cache_hits_total[1m])) or vector(0)) + (sum(rate(cache_misses_total[1m])) or vector(0)), 0.001)
```

Grafana は `http://localhost:${GRAFANA_PORT:-3000}` で開きます。`GRAFANA_PORT` を変えた場合は、そのポートを使ってください。ログインは `admin` / `admin` です。Dashboards から `Shortlink` フォルダの `Shortlink RED and Cache` を開きます。期待するパネルは `Request Rate`、`Error Rate`、`Latency p95`、`Cache Hit Ratio` です。Prometheus の scrape interval は 15 秒なので、アクセス直後は少し待ってから更新してください。

確認が終わったら片付けます。


## 今日のまとめ

今日は、URL 短縮サービスを観察できる形にしました。可観測性の三本柱は、メトリクス、ログ、トレースです。Day 12 では Prometheus メトリクスと JSON 構造化ログを実装し、トレースは概念として扱いました。

メトリクスでは、RED メソッドを軸に `http_requests_total` と `http_request_duration_seconds` を追加しました。リクエスト数は counter、レイテンシは histogram です。平均だけでは遅い一部のリクエストを見逃しやすいため、`histogram_quantile` で p95 を見ます。

ラベル設計では、`/{code}` を raw code のまま扱わず、`redirect` に正規化しました。Prometheus はラベル値の組み合わせごとに時系列を作るため、短縮コードのように種類が増え続ける値を入れるとカーディナリティが爆発します。

ログは `log/slog` の JSON handler で構造化しました。`method`、`path`、`status`、`duration_ms` のようなフィールドがあるため、あとから機械的に絞り込めます。これは単なる grep より強く、集約基盤へ流したときにも同じフィールドで検索できます。

実検証では Prometheus target が up になり、Grafana の `/api/health` は 200 を返し、アプリログには `method/path/status/duration_ms` が出て、`http_requests_total{method="GET",route="redirect",status="302"}` が実カウントされることを確認しています。
