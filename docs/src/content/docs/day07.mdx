### ベースラインとは何か

ベースラインは、改善前の基準値です。

改善は、比較できて初めて改善です。
Day 8 の Redis キャッシュ、Day 11 の複数レプリカや HPA でも、今日の数値が比較の物差しになります。

### スループットとレイテンシ

負荷試験で最初に見るのは、スループットとレイテンシです。

スループットは、単位時間あたりにどれだけ処理できたかです。
HTTP サービスなら、1 秒あたりのリクエスト数、つまり req/s で見ることが多いです。
k6 の出力では `http_reqs` の右側に `26.97/s` のような値が出ます。

レイテンシは、1 リクエストが返ってくるまでにどれだけ時間がかかったかです。
k6 の出力では `http_req_duration` に `avg`、`p(90)`、`p(95)`、`max` などが出ます。

スループットとレイテンシは別の指標です。
たくさん処理できていても、一部のユーザーだけ極端に遅いかもしれません。
逆に、1 リクエストは速くても、同時アクセスが増えた瞬間に失敗するかもしれません。
そのため、負荷試験では `http_reqs` と req/s、`http_req_duration`、`http_req_failed` と `checks` を一緒に見ます。

### 平均は嘘をつく

レイテンシを見るとき、平均値だけに頼ると危険です。
平均は便利ですが、ユーザー体験の悪い部分を隠すことがあります。

たとえば 10 件中 9 件は 2ms、1 件だけ 200ms なら、平均はおよそ 21.8ms です。
平均だけを見ると悪くなさそうですが、200ms を踏んだユーザーにとっては遅い体験です。

そこでパーセンタイルを見ます。
p50 は 50%、p95 は 95%、p99 は 99% のリクエストがその時間以内に終わったという意味です。
p50 は中央値とも呼ばれます。

p95 が 100ms なら、100 件中 95 件は 100ms 以内に返り、残り 5 件はそれより遅い可能性があります。
つまり p95 は、平均よりも「遅い側の体験」に目を向けるための指標です。
本番サービスでは、平均が良くても p95 や p99 が悪いと問題になります。

### k6 の VU モデル

今日使う負荷試験ツールは k6 です。
k6 では、スクリプトの `default` 関数を繰り返し実行する仮想ユーザーを VU、Virtual User と呼びます。
1 VU は、1 人のユーザーが「リクエストを投げる、少し待つ、また次の操作をする」という流れを繰り返すイメージです。

`load/day07-baseline.js` では、`ramping-vus` を使っています。

```js title="load/day07-baseline.js"
export const options = {
  scenarios: {
    baseline: {
      executor: 'ramping-vus',
      stages: [
        { duration: '30s', target: 20 },
        { duration: '1m', target: 50 },
        { duration: '30s', target: 0 },
      ],
    },
  },
};
```

これは、最初の 30 秒で 0 VU から 20 VU へ増やし、次の 1 分で 50 VU へ増やし、最後の 30 秒で 0 VU へ戻す、合計 2 分間の負荷試験です。
段階的に増やすことで、どのあたりからレイテンシや失敗率が変わるのかを見やすくします。

### thresholds は性能のテスト

k6 の `thresholds` は、負荷試験の合格条件です。
単に数値を見るだけではなく、「この条件を満たさなければ失敗」と定義できます。

```js title="load/day07-baseline.js"
thresholds: {
  http_req_duration: ['p(95)<100'],
  http_req_failed: ['rate<0.01'],
},
```

`http_req_duration: ['p(95)<100']` は p95 レイテンシが 100ms 未満、`http_req_failed: ['rate<0.01']` は HTTP 失敗率が 1% 未満であることを期待します。
threshold が失敗すると、k6 の終了コードは 0 ではなくなります。
CI では、性能条件を満たさない変更を失敗として扱えます。

### スクリプトのウォークスルー

今日の負荷試験スクリプトは `load/day07-baseline.js` です。
接続先は `BASE_URL` 環境変数で変えられ、指定しなければ `http://localhost:8080` です。

```js title="load/day07-baseline.js"
const BASE_URL = __ENV.BASE_URL || 'http://localhost:8080';
```

最初に `setup` が実行されます。
ここでは、リダイレクト試験で使う短縮 URL を 100 件作っています。

```js title="load/day07-baseline.js"
export function setup() {
  const links = [];

  for (let i = 0; i < 100; i += 1) {
    const url = `https://example.com/day07/seed/${i}`;
    const res = createLink(url);
    const code = responseCode(res);
    const ok = check(res, {
      'setup create returns 201': (r) => r.status === 201,
      'setup create has code': () => Boolean(code),
    });
```

`setup` で作った `links` は、`default` 関数に渡されます。
負荷試験本体では、90% の確率で既存の短縮 URL へアクセスし、10% の確率で新しい短縮 URL を作ります。

```js title="load/day07-baseline.js"
export default function (data) {
  if (Math.random() < 0.9) {
    const link = data.links[Math.floor(Math.random() * data.links.length)];
    const res = http.get(`${BASE_URL}/${link.code}`, {
      redirects: 0,
      tags: { name: 'GET /{code}' },
    });
```

URL 短縮サービスでは、1 回作った短縮 URL が何度もクリックされるため、一般に作成よりリダイレクトのほうが多くなります。
そのため、今日のシナリオは create 10%、redirect 90% の混合にしています。

リダイレクトでは `redirects: 0` を指定しています。
これは、k6 にリダイレクト先の `https://example.com/...` まで追いかけさせないためです。
測りたいのは shortlink アプリが `302` と `Location` を返すまでの時間であり、外部サイトの応答時間ではありません。

POST 側では `201` と `code` の存在を確認し、GET 側では `302` と `Location` が期待した URL と一致することを確認します。

最後に `sleep(1)` があります。
これは、各 VU が 1 回操作したあとに 1 秒待つという意味です。
待ち時間を入れることで、休みなく連打する機械的な負荷ではなく、少しだけ人間の操作に近い形にしています。

### pprof を別ポートに出す理由

Go には `net/http/pprof` という標準のプロファイリング機能があります。
CPU の使われ方、メモリの使われ方、goroutine の状態などを HTTP 経由で調べられます。

ただし、pprof はアプリの内部状態を見せる入口です。
本番 API と同じポートに何となく出すものではありません。
そのため、このリポジトリでは `DEBUG_ADDR` が設定されたときだけ、別の HTTP サーバとして pprof を公開します。

```go title="app/cmd/server/main.go"
func newDebugServer() *http.Server {
	addr := os.Getenv("DEBUG_ADDR")
	if addr == "" {
		return nil
	}

	mux := http.NewServeMux()
	mux.HandleFunc("/debug/pprof/", pprof.Index)
	mux.HandleFunc("/debug/pprof/cmdline", pprof.Cmdline)
	mux.HandleFunc("/debug/pprof/profile", pprof.Profile)
	mux.HandleFunc("/debug/pprof/symbol", pprof.Symbol)
	mux.HandleFunc("/debug/pprof/trace", pprof.Trace)
```

`heap` は `/debug/pprof/` の一覧から開けます。
そして `DEBUG_ADDR` が空なら `nil` を返し、デバッグサーバを起動しません。

```go title="app/cmd/server/main.go"
debugServer := newDebugServer()

if debugServer != nil {
	go func() {
		log.Printf("debug server listening on %s", debugServer.Addr)
		errCh <- debugServer.ListenAndServe()
	}()
}
```

別ポートにする理由は、通常のユーザー向け API とデバッグ用 API を分け、`DEBUG_ADDR` を設定したときだけ明示的に有効化し、将来の本番構成で内部ネットワークからだけ見せる設計にしやすくするためです。

pprof の基本として、まず見るのは `profile` と `heap` です。
`profile` は指定した秒数のあいだ、どの関数で CPU 時間を使っていたかを見ます。
`heap` は、どの経路でメモリが確保されているかを見るメモリプロファイルです。

今日の段階では、pprof で深い最適化をしなくて構いません。
大事なのは、負荷をかけながら内部を観察する入口を持つことです。

## 明日の予告

Day 8 では、Redis キャッシュを入れて読み取りを速くします。
URL 短縮サービスは、作成よりリダイレクトのほうが多い read-heavy なサービスです。
今日測った p95 3.04ms、26.97 req/s というベースラインと比べながら、キャッシュがどの数値に効くのかを見ていきます。
