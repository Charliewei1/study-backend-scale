この教材では、URL 短縮サービス「shortlink」を 1 日ずつ育てます。最初は Go の標準ライブラリだけで動く小さな HTTP サーバから始め、永続化、テスト、Docker、Kubernetes、負荷試験、キャッシュ、可観測性、レートリミット、分散設計へ進みます。

大事にするのは、道具の名前を覚えることではありません。なぜその設計が必要になるのか、どの負荷や運用上の制約に効くのかを、実装と計測を通して確かめることです。

## 15日間の概要

| 日 | タイトル | 主なテーマ |
| --- | --- | --- |
| Day 1 | Go 入門と最小の URL 短縮サーバ | `net/http`、パッケージ構成、base62、メモリ保存 |
| Day 2 | API 設計とテスト文化 | JSON エラー、URL バリデーション、`httptest`、table-driven test |
| Day 3 | 永続化とインターフェース設計 | Storage インターフェース、SQLite、`context.Context`、差し替えやすい設計 |
| Day 4 | Go の並行処理とクリック統計 | goroutine、channel、race detector、graceful shutdown |
| Day 5 | Docker でコンテナ化 | multi-stage build、distroless、イメージレイヤ、非 root 実行 |
| Day 6 | Docker Compose と Postgres 移行 | Compose、Postgres、healthcheck、サービス名 DNS、接続プール |
| Day 7 | 計測: k6 ベースラインと pprof | レイテンシ、スループット、p95、k6、pprof |
| Day 8 | Redis キャッシュ: 読み取りを速くする | read-heavy ワークロード、cache-aside、TTL、キャッシュヒット率 |
| Day 9 | Kubernetes 入門: kind で動かす | Pod、Deployment、ReplicaSet、Service、kubectl の基本 |
| Day 10 | k8s 設定・ヘルスチェック・ローリング更新 | ConfigMap、Secret、probe、resources、RollingUpdate |
| Day 11 | 水平スケールと HPA | ステートレス化、ランダム ID、衝突確率、Horizontal Pod Autoscaler |
| Day 12 | 可観測性: Prometheus と structured logging | メトリクス、ログ、RED メソッド、PromQL、JSON ログ |
| Day 13 | レートリミットと回復性: 入口で守る | token bucket、429、タイムアウト、バックオフ、graceful degradation |
| Day 14 | さらなるスケール: シャーディングと分散の理論 | リードレプリカ、シャーディング、consistent hashing、CAP 定理 |
| Day 15 | 総仕上げ: フルスタックデプロイと最終計測 | 全体アーキテクチャ、最終 k6、改善比較、次の学習ロードマップ |

## 対象読者

- Go で Web API を作りながら、バックエンド開発の基礎を固めたい人
- Docker や Kubernetes を、手順だけでなく「何を解決する道具か」から理解したい人
- スケーラビリティ、キャッシュ、可観測性、レートリミットを実装と計測で学びたい人
- 小さなサービスが本番運用に近づく過程を、段階的に追体験したい人

Go、Docker、Kubernetes の経験が浅くても進められる構成にします。一方で、各日で扱う設計判断は実務でもそのまま使うものです。すでに経験がある人は、なぜその選択をするのかを説明できるか確認しながら進めてください。

## 進め方

このコースは**読むだけでは進みません**。毎日、自分でコードを書きます。

リポジトリのルートに `./study` コマンドがあります。gitのタグ操作は中に隠してあるので、
Day番号だけ意識すれば進められます。

```bash
./study start 1
```

これで `work/` に、その日の演習が用意されます。中身はこうなっています。

| 中身 | 意味 |
| --- | --- |
| 前日までの完成コード | 自分が書いた続きとして、そのまま読めます |
| `panic("TODO: ...")` の関数 | **今日あなたが書く場所** |
| その日のテスト | 今日の仕様書。これが緑になれば合格 |

1日の流れは、いつも同じ4手です。

```bash
./study test      # ① まず落ちることを確認する（何が足りないかが分かる）
                  # ② work/ の TODO を埋める
./study test      # ③ 通るまで直す
./study answer    # ④ 模範解答と見比べる
```

### コマンド一覧

| コマンド | すること |
| --- | --- |
| `./study` | いまどこにいるか |
| `./study days` | 15日間の一覧 |
| `./study start 3` | Day03の演習を用意する |
| `./study test` | その日の合格条件をチェックする |
| `./study test --full` | 重い検証まで走らせる（`docker build`、kind、k6） |
| `./study todo` | 残っているTODOの一覧 |
| `./study hint` | その日の解説を読む |
| `./study run` | 書いたサーバを起動して `curl` で叩く |
| `./study answer` | 自分のコードと模範解答の差分 |
| `./study peek <パス>` | 模範解答をそのまま見る |
| `./study reset` | 今日を最初からやり直す |

### 日によって「合格条件」が変わります

このコースの後半は、成果物がGoのコードとは限りません。`./study test` は、その日の主役に合わせて
確かめる内容を変えます。

| Day | 成果物 | 確かめること |
| --- | --- | --- |
| 1〜4, 6, 8, 11〜14 | Goのコード | `go build` / `go vet` / `go test`（Day4以降は `-race`） |
| 5 | Dockerfile | multi-stage、非root、`CGO_ENABLED=0`。`--full` で実際にビルドして起動 |
| 7 | k6スクリプト | thresholds と pprof。`--full` で実際に負荷をかける |
| 9, 10, 15 | k8sマニフェスト | 必須リソースと設定。`--full` で kind クラスタに載せる |

### 読む順番

1. その日のページの「今日つくるもの」で、満たすべき契約を確認する。
2. `./study start N` で演習を用意し、`./study test` が落ちることを見る。
3. 「解説」を読む。実装がすぐ欲しくなったら `<details>` を開けますが、**先に自分で書いてから**。
4. `./study test` が通ったら `./study answer` で模範解答と比べる。
5. クイズに答え、間違えた問題は本文とコードに戻って確認する。
6. Day 7 以降は計測値を記録し、改善前後の数字を比較する。

このコースの軸は「動いた」で終わらせないことです。URL 短縮という小さな題材でも、読み取りが多い、短い ID が必要、リダイレクトが遅いと体験が悪い、複数レプリカでローカル状態が壊れる、という現実的な制約が出てきます。その制約に対して、コード、インフラ、計測のどこで対応するのかを毎日少しずつ増やしていきます。
