## 今日のゴール

- 保存先を `Storage` インターフェースとして切り出す理由を説明できるようになる。
- Go のインターフェースが、明示的な `implements` なしで暗黙的に満たされることを理解する。
- `MemoryStore` と `SQLiteStore` を、同じハンドラから差し替えて使う流れを読めるようになる。
- `database/sql` の `*sql.DB` が単一接続ではなくコネクションプールであることを理解する。
- `modernc.org/sqlite` を使う理由として、cgo 不要で扱いやすいことを説明できるようになる。
- `context.Context` を HTTP リクエストから storage 層へ伝播する意味を理解する。
- `ErrNotFound` のようなセンチネルエラーと `errors.Is` の使い方に慣れる。
- `STORAGE=sqlite` で起動し、再起動後も短縮リンクが残ることを確認する。

## 今日つくるもの

今日は `work/app/` の保存層と、その保存層を使うハンドラ・起動処理を実装します。
ここでは完成コードではなく、満たすべき契約だけを確認しておきましょう。

- `internal/storage/storage.go` を作り、`Link`、`ErrNotFound`、次のメソッドを持つ `Storage` インターフェースを定義する。
  - `Save(ctx context.Context, code, url string) error`
  - `Load(ctx context.Context, code string) (string, error)`
  - `Get(ctx context.Context, code string) (Link, error)`
- `internal/storage/memory.go` の `Save` と `Load` を上のシグネチャへ変更し、`Get(ctx context.Context, code string) (Link, error)` を実装する。
  - 保存したコードは `Load` と `Get` で取得でき、同じコードを再保存すると新しい URL へ更新されること。
  - コードが存在しない場合は `ErrNotFound` を返し、キャンセル済みの context はエラーとして扱うこと。
- `internal/storage/sqlite.go` を作り、次の関数とメソッドを実装する。
  - `NewSQLiteStore(ctx context.Context, path string) (*SQLiteStore, error)`
  - `(*SQLiteStore).init(ctx context.Context) error`
  - `(*SQLiteStore).Close() error`
  - `(*SQLiteStore).Save(ctx context.Context, code, url string) error`
  - `(*SQLiteStore).Load(ctx context.Context, code string) (string, error)`
  - `(*SQLiteStore).Get(ctx context.Context, code string) (Link, error)`
  - 指定した SQLite ファイルを開いて必要なテーブルを用意し、保存・取得・同じコードの更新ができること。存在しないコードは `ErrNotFound` として扱うこと。
- `internal/handler/handler.go` で保存先を `storage.Storage` として受け取り、`writeStorageError(w http.ResponseWriter, err error)` を実装する。
  - HTTP リクエストの context を保存層へ渡すこと。
  - `ErrNotFound` は `404` と `{"error":"link not found"}`、それ以外の保存エラーは `500` と `{"error":"internal server error"}` に変換すること。
  - 既存の API 契約を保つこと。作成は `201 Created`、取得はリンク情報の JSON、リダイレクトは `302 Found` を返す。
- `cmd/server/main.go` に `newStore() (storage.Storage, func())` を実装する。
  - `STORAGE` が空または `memory` ならメモリ、`sqlite` なら `SQLITE_PATH` の SQLite を使うこと。`SQLITE_PATH` が空なら `data.db` を使うこと。
  - SQLite の接続は終了時に閉じ、未対応の `STORAGE` は起動エラーとして扱うこと。
- 合格条件は、TODO を残さず、`./study test` が行う `go build ./...`、`go vet ./...`、`go test ./...` をすべて通すこと。

## 解説

Day 1 では、短縮コードと URL の対応を `map[string]string` に保存しました。
Day 2 では、API のエラー形式とテストを整えました。
Day 3 では、いよいよ保存先を永続化します。

永続化とは、プロセスが止まってもデータが残るようにすることです。
メモリ保存は速くて単純ですが、サーバを再起動すると中身が消えます。
URL 短縮サービスでは、作った短縮 URL が再起動後に使えなくなるのは困ります。

今日の実装では、SQLite ファイルへ保存できる `SQLiteStore` を追加しています。
ただし、単に SQLite のコードをハンドラへ直接書き込むのではありません。
まず `Storage` インターフェースを作り、ハンドラが具体的な保存先に依存しすぎない形へ変えています。

### なぜ Storage インターフェースを切るのか

Day 2 までのハンドラは、保存先として `MemoryStore` を直接受け取っていました。
これは小さいうちは分かりやすい設計です。
しかし、保存先が SQLite、Postgres、Redis と増えていくと、ハンドラが具体的な実装を知りすぎると変更しづらくなります。

そこで Day 3 では、ハンドラが必要とする操作だけを `Storage` インターフェースにまとめます。

```go title="app/internal/storage/storage.go"
type Storage interface {
	Save(ctx context.Context, code, url string) error
	Load(ctx context.Context, code string) (string, error)
	Get(ctx context.Context, code string) (Link, error)
}
```

ハンドラが知りたいことは、「保存できるか」「コードから URL を読めるか」「メタ情報を取れるか」です。
それができるなら、裏側が `map` でも SQLite でも構いません。
この考え方を依存性の注入と呼びます。

依存性の注入は、部品を中で直接作らず、外から渡す設計です。
実コードでも `handler.New(shortener *shortener.Shortener, store storage.Storage, baseURL string)` という形で、保存先を外から受け取っています。
この形にしておくと、テストでは軽い `MemoryStore` を渡せます。
ローカルで永続化を見たいときは `SQLiteStore` を渡せます。
Day 6 で Postgres に進むときも、ハンドラの主な関心は変えずに保存先を増やせます。

さらに後日、Redis キャッシュを足すときにもこの考え方が効いてきます。
HTTP の入口、保存、キャッシュ、分析を分けておくと、1 つの部品を差し替えても全体を壊しにくくなります。

### Go のインターフェースは暗黙的に満たす

Go には、Java や TypeScript のように `implements Storage` と書く場所がありません。
ある型が `Storage` に必要なメソッドをすべて持っていれば、その型は自動的に `Storage` として扱えます。
これを暗黙的実装と呼びます。

`MemoryStore` は、次の 3 つのメソッドを持っています。

```go title="app/internal/storage/memory.go"
func (s *MemoryStore) Save(ctx context.Context, code, url string) error
func (s *MemoryStore) Load(ctx context.Context, code string) (string, error)
func (s *MemoryStore) Get(ctx context.Context, code string) (Link, error)
```

`SQLiteStore` も同じ 3 つのメソッドを持っています。

```go title="app/internal/storage/sqlite.go"
func (s *SQLiteStore) Save(ctx context.Context, code, url string) error
func (s *SQLiteStore) Load(ctx context.Context, code string) (string, error)
func (s *SQLiteStore) Get(ctx context.Context, code string) (Link, error)
```

そのため、どちらも `storage.Storage` として `handler.New` に渡せます。
インターフェースは「この型です」と名乗る仕組みではなく、「この操作ができます」と約束する仕組みです。

この性質は、テストでも便利です。
本物の SQLite ファイルを使わずに、テスト用の保存先を渡すことができます。
Day 2 からあるハンドラテストは、いまも `storage.NewMemoryStore()` を `handler.New` に渡しています。
ハンドラは `storage.Storage` だけを要求します。
`MemoryStore` がそのメソッドを満たすので、そのまま渡せます。
これが、インターフェースを小さく切る大きな利点です。

### ErrNotFound とセンチネルエラー

Day 3 では、見つからないことを `ErrNotFound` で表すようにしています。

```go title="app/internal/storage/storage.go"
var ErrNotFound = errors.New("link not found")
```

このように、パッケージで定義して比較対象にするエラーをセンチネルエラーと呼びます。
`MemoryStore` は、コードが見つからないときにこのエラーを返します。

SQLite では、`database/sql` が行なしを `sql.ErrNoRows` として返します。
しかし、ハンドラに `sql.ErrNoRows` を直接知らせると、ハンドラが SQLite や `database/sql` の事情を知ることになります。
そこで storage 層で `ErrNotFound` へ変換します。

<details>
<summary>実装を見る（先に自分で書いてから開こう）</summary>

```go title="app/internal/storage/sqlite.go"
if err := s.db.QueryRowContext(ctx, query, code).Scan(&link.Code, &link.URL); err != nil {
	if errors.Is(err, sql.ErrNoRows) {
		return Link{}, ErrNotFound
	}
	return Link{}, fmt.Errorf("get link: %w", err)
}
```

</details>

ハンドラ側は、保存先がメモリか SQLite かを気にせず `writeStorageError` の中で `errors.Is(err, storage.ErrNotFound)` と判定します。
`errors.Is` を使う理由は、エラーがラップされても判定できるからです。
Go では、原因を残したまま文脈を足すために `fmt.Errorf("...: %w", err)` をよく使います。
単純な `err == storage.ErrNotFound` だと、ラップされたエラーを見逃します。
そのため、外側の層で種類を判定するときは `errors.Is` を使うのが安全です。

### context.Context を第一引数で受け取る

`Storage` の各メソッドは、`Save(ctx context.Context, ...)` のように第一引数に `context.Context` を受け取ります。
Go では、キャンセルやタイムアウトを伝える必要がある関数では、`context.Context` を第一引数に置くのが慣習です。
HTTP リクエストにも context が付いています。
クライアントが接続を切ったり、サーバ側でタイムアウトを設定したりすると、その情報を `r.Context()` から下の層へ渡せます。

ハンドラでは、保存や取得に `r.Context()` を渡しています。
メモリ保存はとても速いのでキャンセルが目に見えることは少ないですが、`MemoryStore` も `ctx.Err()` を確認しています。
SQLite 側では、`ExecContext` や `QueryRowContext` に context を渡しています。

今後 Postgres や Redis のようなネットワーク越しの保存先へ進むと、context の重要性はさらに上がります。
リクエストがすでにキャンセルされているのに、データベース処理だけが残り続けるのは避けたいからです。

### database/sql とコネクションプール

SQLite 実装は、標準ライブラリの `database/sql` を使っています。

```go title="app/internal/storage/sqlite.go"
type SQLiteStore struct {
	db *sql.DB
}
```

ここで大事なのは、`*sql.DB` は 1 本のデータベース接続そのものではない、という点です。
`*sql.DB` は、必要に応じて接続を開き、使い終わった接続を再利用するコネクションプールです。

HTTP サーバでは、複数のリクエストが同時に来ます。
そのたびに接続を作って捨てると、遅くなり、リソースも無駄になります。
`database/sql` は、接続の再利用や待ち合わせを管理する共通の仕組みを提供します。
ただし、SQLite は 1 ファイルを直接扱うデータベースなので、同時書き込みには制約があります。
`*sql.DB` のプールがあっても、SQLite を使う限りスケールの主役にはならず、Day 6 で Postgres へ進む理由もここにあります。

SQLite の初期化では、`sql.Open("sqlite", path)` で `*sql.DB` を作り、続けて `CREATE TABLE IF NOT EXISTS links (...)` を `ExecContext` で実行します。
`links` テーブルでは、`code` が主キーです。
同じコードを 2 回保存した場合は、`ON CONFLICT` で URL を新しい値へ更新します。

```go title="app/internal/storage/sqlite.go"
ON CONFLICT(code) DO UPDATE SET url = excluded.url;
```

Day 3 時点では、短縮コード生成器のカウンタはまだメモリ上にあります。
そのため、サーバ再起動後に新しいリンクを作ると、また `"1"` から採番されます。
Day 3 の実装では同じコードを保存すると既存 URL を更新するため、再起動後に新しいリンクを作ると既存の `"1"` が上書きされる可能性があります。
これは根本解決ではありません。
複数台構成でも安全な ID 採番は、Day 11 でランダム base62 へ進むときに扱います。
今回の手順では、再起動後に新しいリンクを作る前に「以前作ったリンクが読めること」を確認します。

### modernc.org/sqlite を選んだ理由

Go で SQLite を使うドライバはいくつかあります。
この教材では `modernc.org/sqlite` を `_ "modernc.org/sqlite"` として import しています。
先頭の `_` は、パッケージを直接名前で呼ばないけれど、初期化処理だけを使う import です。
SQLite ドライバは、この初期化処理で `database/sql` に `"sqlite"` というドライバ名を登録します。
そのため、あとで `sql.Open("sqlite", path)` と書けます。

`modernc.org/sqlite` を選んでいる主な理由は、cgo が不要なことです。
cgo は Go から C のコードを呼ぶ仕組みで、強力ですが、ビルド環境やクロスコンパイルが複雑になりやすい面があります。
この教材では、Day 5 以降に Docker や Kubernetes へ進みます。
その前段階では、できるだけ Go のビルド体験を単純にしておきたいので、pure Go で使える SQLite ドライバを選んでいます。

もちろん、本番の大規模構成で SQLite を共有データベースとして使うわけではありません。
SQLite は、ローカル開発や小さな単体プロセスではとても扱いやすい選択です。
Day 6 では、ネットワーク越しに複数プロセスから使える Postgres へ進みます。

### 起動時に保存先を切り替える

保存先の切り替えは `cmd/server/main.go` にあります。
`STORAGE` 環境変数が空、または `memory` ならメモリ保存です。
`sqlite` なら SQLite 保存です。

<details>
<summary>実装を見る（先に自分で書いてから開こう）</summary>

```go title="app/cmd/server/main.go"
func newStore() (storage.Storage, func()) {
	switch os.Getenv("STORAGE") {
	case "", "memory":
		return storage.NewMemoryStore(), func() {}
	case "sqlite":
		path := os.Getenv("SQLITE_PATH")
		if path == "" {
			path = "data.db"
		}

		store, err := storage.NewSQLiteStore(context.Background(), path)
		if err != nil {
			log.Fatalf("initialize sqlite storage: %v", err)
		}
		return store, func() {
			if err := store.Close(); err != nil {
				log.Printf("close sqlite storage: %v", err)
			}
		}
	default:
		log.Fatalf("unsupported STORAGE %q; want memory or sqlite", os.Getenv("STORAGE"))
		return nil, func() {}
	}
}
```

`newStore` は、`storage.Storage` と終了時のクリーンアップ関数を返します。
メモリ保存では閉じるものがないので、空の関数を返します。
SQLite 保存では、最後に `store.Close()` して `*sql.DB` の接続プールを閉じます。

`main` は、返ってきた保存先を `handler.New(shortener.New(), store, baseURL)` に渡すだけです。
このように、アプリの入口で具体的な実装を選び、内側のハンドラはインターフェースだけを見る形にしておくと、変更点を狭くできます。

SQLite 実装のテストでは、`t.TempDir()` でテストごとの一時 DB を作り、`t.Cleanup` で `store.Close()` を呼んでいます。
また、見つからないケースは `errors.Is(err, ErrNotFound)` で確認しています。
テストが見ているのは SQLite 内部の `sql.ErrNoRows` ではなく、storage パッケージが外へ出す契約です。

</details>

### 3. `./study run` で実際に叩く

まず、古い確認用 DB があれば消し、1 つ目のターミナルでサーバを起動します。

```bash
rm -f /tmp/shortlink-day03.db
STORAGE=sqlite SQLITE_PATH=/tmp/shortlink-day03.db ./study run
```

期待するログは次の形です。

```txt
shortlink server listening on :8080
```

別のターミナルで、短縮リンクを作ります。

```bash
curl -i -X POST http://localhost:8080/api/links \
  -H 'Content-Type: application/json' \
  -d '{"url":"https://example.com/articles/sqlite"}'
```

新しい DB で最初の作成なら、期待出力は次の形です。

```http
HTTP/1.1 201 Created
Content-Type: application/json
Location: http://localhost:8080/1

{"code":"1","short_url":"http://localhost:8080/1"}
```

念のため、リダイレクトを確認します。

```bash
curl -i http://localhost:8080/1
```

```http
HTTP/1.1 302 Found
Location: https://example.com/articles/sqlite
```

次に、1 つ目のターミナルで `Ctrl+C` を押してサーバを止めます。
同じ SQLite ファイルを指定して、もう一度起動します。

```bash
STORAGE=sqlite SQLITE_PATH=/tmp/shortlink-day03.db ./study run
```

再起動後に、同じ短縮コードへアクセスします。

```bash
curl -i http://localhost:8080/1
```

期待出力は、再起動前と同じ `302 Found` です。

```http
HTTP/1.1 302 Found
Location: https://example.com/articles/sqlite
```

メタ情報 API でも確認できます。

```bash
curl -i http://localhost:8080/api/links/1
```

```http
HTTP/1.1 200 OK
Content-Type: application/json

{"code":"1","url":"https://example.com/articles/sqlite","short_url":"http://localhost:8080/1"}
```

これで、リンクの対応がプロセス内メモリではなく SQLite ファイルに残っていることを確認できました。
同じ手順を `STORAGE=memory` で試すと、再起動後の `/1` は `404 Not Found` になります。
この差が、永続化の効果です。

存在しないコードも確認しておきます。

```bash
curl -i http://localhost:8080/missing
```

```http
HTTP/1.1 404 Not Found
Content-Type: application/json

{"error":"link not found"}
```

保存先が SQLite でも、ハンドラから見るとエラーは `storage.ErrNotFound` です。
そのため、メモリ保存と同じ JSON エラーを返せます。

## 今日のまとめ

今日は、保存先を `Storage` インターフェースとして切り出し、メモリ保存と SQLite 保存を差し替えられる形にしました。
ハンドラは `Save`、`Load`、`Get` という必要な操作だけを知り、具体的な保存方法は起動時に選びます。
これにより、テストでは `MemoryStore`、ローカル永続化では `SQLiteStore` を使えます。

Go のインターフェースは暗黙的実装です。
`MemoryStore` と `SQLiteStore` は、`Storage` が求めるメソッドを持っているため、明示的な `implements` なしで同じ保存先として扱えます。
この小さな抽象化が、Day 6 の Postgres、Day 8 の Redis、Day 11 以降の水平スケールへ進む土台になります。

SQLite 実装では、`database/sql` の `*sql.DB` を使いました。
`*sql.DB` は単一接続ではなくコネクションプールです。
`modernc.org/sqlite` は cgo 不要で使えるため、これから Docker や Kubernetes へ進む教材の流れに合っています。

また、`context.Context` を HTTP ハンドラから storage 層へ渡しました。
キャンセルやタイムアウトを下へ伝えるためです。
見つからないコードは `ErrNotFound` というセンチネルエラーに統一し、ハンドラでは `errors.Is` で判定しました。
保存先の内部事情を外へ漏らさないことも、差し替えやすい設計の一部です。
